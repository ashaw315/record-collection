Sections in this file are §M.1 onward. M is for modal. M is free: Code confirms it is none of the index’s file keys, no section prefix and no id anywhere, and both grammars accept M ids from dbeebfd. It is an index input, M, from 7030141, the commit in which Code took the drop carrying its governs rows and steps 81 and 82 and added the input.

The record modal, M — build target

This rules the record modal: the sleeve turning over, and the gatefold opening. Nothing in it is built, so there are no captures and this file shows no specimen. Every ruling about how something looks or moves is provisional until its build step captures it. Code’s survey of the build is the source for what exists today. This is the first thing in the app to draw the gatefold. The shelf query fetches both inside images, but no wall component draws them. The wall draws the cover, and the back where there is a back photo, so until now the gatefold has appeared only as gallery tiles.

M.1 · Where the modal opens, and what it is

The modal opens from the record page only. This is Adam’s ruling. The wall’s pull stays as it is, so the modal is not the pulled record’s next state, and nothing in §W changes.

The trigger is the displayed cover itself. It becomes a button whose accessible name is “Open the sleeve”. It adds no control to the page, so the closed screen’s composition does not change. On a pointer device its signs are the pointer cursor and §M.6’s focus ring. On a touch device it has no sign at all, and readers on a phone are not expected to find it from the page. That is the cost of adding nothing to a closed screen. A visible sign would have to go on the record page, and the obvious place, the paper below the cover, is ruled empty by §23: “The paper below the cover is the band’s, as in the render, and carries nothing.” So a sign there would owe a withdrawal against §23 and its own pass, which is Adam’s call and not this file’s. Discoverability cannot be checked by capture, since no capture shows a cursor, and on a phone there is nothing to show. Two checks stand in for it. A tap test shows the trigger works on touch, and Adam reports in words whether he found it unprompted on his own phone.

Nothing in the build binds a click on the displayed cover, Code confirms, so the trigger takes nothing from the page. The page’s cover is §33’s: Adam ruled it cropped to fill within §33’s 95% bound and fitted beyond it.

The modal is a view of the object, not a dialog over the page. It covers the whole viewport on opaque paper, with no dimming, shadow or rounded panel, because the system has no elevation. Its top row is 53, like the header’s, with a hairline below it and CLOSE at the right on the 18 inset. Below that row the sleeve is centred, closed or open, with its controls in one row beneath it, as §M.4 sizes it. Escape and CLOSE dismiss it, and focus returns to the cover. Tab cycles within the modal while it is open.

Back closes the modal. Opening it adds one history entry at the same URL, so the address does not change, and Back returns to the record page with the modal closed instead of leaving it. On a phone, Back is the obvious gesture for “close this”, and a full-viewport view that Back skips past would take the reader off the record. CLOSE and Escape step back through that entry, so it never lingers. The cost: the modal has no address of its own, so it cannot be linked to, and a reload with it open returns to the record page with it closed. Nothing in the app links to a face, so that costs nothing today.

M.2 · Which photo of each face

Every face shows the newest photo of its type: the front the newest cover, as §61 rules for the page, the back the newest back, and each inside leaf the newest of its own type. §61’s reason applies to every face, not only the cover: Adam’s own photograph of his own copy is a better source than a catalogue image, and an upload should never sit unseen behind an older one. So the front in the modal is always the cover the page shows.

The wall moves to newest-first too, and this file does not keep two rules. A reader who pulls a record and later opens its modal would otherwise see two different backs of one sleeve, and nothing about the wall justifies an older photo there. No §W ruling orders the backs, so no §W withdrawal is owed. Code confirms that “oldest” does not occur in the wall’s target and no §W prose states an order. The oldest back is built behaviour, and the shelf query’s own comment gives its reason as matching the gallery’s first image. That reason gives way to §61’s, because the gallery shows every image and its first is not a face. The change is a supersession of built behaviour, so it has its own build step.

That step is verified by a fixture, not a capture. Code counted the collection: one record has a back photo, and it has exactly one, so oldest-first and newest-first look the same on every real record. A capture would show nothing. The evidence is a fixture record carrying two backs with different dates, and a test that the wall and the modal both show the newer.

M.3 · The back with no back photo

The modal’s back is the wall’s plain back, the same face from the same component. §11’s flow 7 rules what it carries: the label and the catalogue number, and no body text. One sleeve has one back, so the wall and the modal must not drift apart, and sharing the component is what stops them. Where a back photo exists, the back is that photo, by §M.2.

Withdrawn within §M.3: the plain back in the record’s stored spine colour. It repeated A19 in SPEC.md §10b, which later sections supersede: settled §5.2 clamps the colour, §W.2 makes it the pulled record’s field, and §W.3 and §W.8 give ink where there is no stored colour. As built, the label and catalogue number are set in the wall’s paper colour on that field, which equals the stored colour only where it already sits inside §5.2’s limits. This target was taken at 7030141, so the sentence was in force, and the entry is owed in its own right, not as a consequence of §10b’s.

The modal’s plain back is the record’s field, filling the square, with the label and catalogue number in paper on it; where the record has no stored colour, it is ink. This points at §5.2 for the clamp and does not restate it. One thing those sections do not reach is ruled here. The plain back has no ground of its own, and on the wall the pull supplies it, but the modal has no pull, so the modal draws the field itself, in the square, from the same computation.

An earlier draft of this section was wrong, from a summary Code has since retracted. It gave the plain back six fields, four of which it does not carry: pressing, matrix, condition and price. It also gave it a sentence for when nothing is recorded, which was in §10b for one day in August before A19 replaced it. When it was corrected, the target was not yet an index input and Code had not committed it, so this was a draft fix.

M.4 · Shape: every photo is fitted, never cropped

The sleeve is drawn as a square, and each photo is fitted inside its square on paper, centred, never cropped. A 1px hairline marks the square’s edge, so the sleeve keeps its shape whatever the photo’s proportions. A crop can cut the edge off a photographed back or an inside leaf, where the sleeve’s printed text is, and the modal exists to show those faces whole. That reason reaches the photographs, not the plain back: the plain back carries no body text and is drawn square, so fitting and cropping are the same for it. The front is fitted as well, so a face does not change size or framing across a turn. The modal’s front and the page’s cover differ by at most 2.5% a side within §33’s bound, measured against the photograph’s long side, which is 2.63% of the square’s side, and match beyond it, because beyond the bound the page fits too. Where they differ, the difference is deliberate: the page composes the cover, and the modal shows the object whole.

The closed sleeve is the same size on every record at a given viewport, and it is centred. It is the largest square that fits the space below the top row, less the controls’ row and an 18 inset. A gatefold record is not drawn smaller, or off-centre, to make room for a spread the reader cannot yet see, since either would be a difference with no visible reason.

So opening moves the sleeve, and on narrow viewports resizes it. In one motion, the front panel rotates about the fold while the whole sleeve moves right by half a square, so the spread ends centred. The fold is the front panel’s left edge, as §M.5 rules, so the front panel swings left to become the left leaf, and the leaf that stays is the right one, where the closed sleeve was. With the spread centred on c, that leaf spans c to c + S, and the closed sleeve spans c − S/2 to c + S/2, so it moves right by S/2. An earlier draft said left, which is the same error as W.15/sign-inverted, a sign stated without being derived. When it was corrected, Code had not committed this target, so this was a draft fix. Where two squares at the closed size do not fit, which on a phone is always, the sleeve also scales down to the largest spread that fits, in the same motion. Folding reverses it. That gives up an earlier draft’s “nothing moves or resizes”, which only held by drawing every gatefold sleeve smaller and off-centre from the start. The sizes are taken once when the modal opens and do not change while it is open. “When the modal opens” means at the press, before the cover travels, so §M.7’s travel moves toward a square already fixed, and the gatefold’s spread is never recomputed while the modal is open. The cover growing into that square is the travel, not a change of size.

M.5 · The turn and the gatefold’s opening

Both are rigid rotations, re-projected every frame, as §W.16 rules for the wall’s turn: corners are never interpolated, so the face turns rather than morphs. The gatefold’s opening, its move and scale in §M.4, are on the same curve as its rotation, so they read as one motion. What this takes from §W.16 is its rigidity, not its projection. The wall is orthographic, which is why W.20/growth-on-travel exists. Face-on, an orthographic turn is only a face narrowing and widening, which does not read as turning a sleeve over.

The turn and the gatefold’s opening are drawn in perspective while they move, and every face is flat and face-on at rest. This gives the modal a depth the rest of the system does not have, and the wall refuses. It is ruled knowingly, for three reasons. The modal is the one place the reader handles a single object rather than looking along a shelf, and turning a sleeve over is what it is for. The depth exists only between faces: every still picture of the modal, every capture, and the whole of reduced motion are as flat as the rest of the app. And the alternative, a turn that reads by shading, would add a light source the system lacks as much as it lacks depth. How strong the perspective is, is not ruled: Code proposes it, and Adam judges it from the recording.

While it turns, the sleeve’s near edge may pass its square, over the face label and the controls, and does not reach the top row. It is the honest consequence of perspective, it lasts a few frames around edge-on, and the alternatives, more room beneath the sleeve or a longer viewing distance, cost something visible at rest, where the modal spends nearly all its time. From Code’s proposal, computed and not yet measured from frames, the swell is about 52 past top and bottom at 1440, reaching TURN OVER, and about 25 at 390, crossing the label only. This is accepted for the perspective Adam picks, and only while the swell stays clear of the top row. If his choice would cross it, the viewing distance lengthens until it does not, and the step reports the swell from frames at the strength he picks.

A press on TURN OVER while the sleeve is turning is ignored. A turn already under way finishes, and the face it lands on is the one the label names, so the state never runs ahead of what the reader sees. The cost: a reader who taps twice quickly gets one turn, not two, and lands where the second tap meant to leave. The same holds for OPEN and FOLD during the gatefold’s opening. The turn is 180 degrees about the sleeve’s vertical centre line. §W.16 pivots about the near edge to keep the record clear of its neighbours on the shelf. The modal has no neighbours, and an in-place turn keeps the sleeve where the reader is looking. The gatefold’s opening rotates the front panel 180 degrees about its left edge, the fold, to become the left leaf, showing the inside left on its reverse and uncovering the inside right in place. That is how a gatefold opens in the hand.

The turn and the gatefold’s opening take the travel’s curve, the ease-out cubic of §M.7, so the modal has one motion character. The reader sees travel and then turn back to back, and two curves there would read as two hands. The durations are not ruled. §W’s figures belong to a pull across a shelf, and none applies to a face-on turn. Code proposes them, and Adam judges the travel and the turn from one recording, so the curve is judged once for both. If he rejects it for either, it changes for both.

Under the reduced-motion setting, the turn and the gatefold’s opening become an immediate change of face, with no rotation and no fade. The opened spread appears at once, centred and at its own size. The reader uses the same controls and gets the same faces in the same order: only the movement between them goes, as it does for the wall’s tilt and transitions. So that the change still reads, a label beneath the sleeve names the face shown, FRONT, BACK or INSIDE, in 11px mono uppercase in the label colour. It shows in every mode, so motion is never the only sign of which face is toward the reader. When the face changes, focus stays on the control that changed it, and the label is announced politely.

M.6 · Controls, hover and focus

The column: the sleeve, the face label and the controls are centred as one column below the top row, with the label 12 below the sleeve and the controls 12 below the label. Those figures were Code’s, stated in its tests, and they are accepted here so they are not a literal no ruling gives. At 390 × 844 the square is 354, and at 1440 × 900 it is 732. 12 is half §G.3’s 24, which keeps the label with the sleeve it names and the controls with the label. The controls’ labels use the header’s type at .12em, as CLOSE does, by §G.1. Every control is §9.3’s: 44 tall, a 1px ink box, no fill, no radius, border-box, with an 11px mono uppercase ink label, 24 apart. TURN OVER shows on the front and on the back, and keeps its label on both, because it is about the record and not about which face is toward the reader, as the wall’s Turn over is. OPEN shows on the front only, and only where the gatefold opens. Once the sleeve is open, the controls are FOLD and CLOSE, so the sleeve is folded shut before it can be turned. There is one CLOSE, in the top row, by §M.1. Open, the control row shows FOLD alone, and the CLOSE this sentence names is the top row’s. The face label in §M.5 says where the reader is.

The gatefold opens only when both inside photos exist. This is Adam’s ruling: nothing in the data says a sleeve is a gatefold, and he chose not to infer it from Discogs’ format text or add a field. Where either leaf is missing, OPEN is absent, not present and inert. Most records will hit this. An inert control would promise every one of them something it cannot do, and nothing on this screen changes that, because photos are added in Manage. The cost is that a reader is not told that adding both leaves makes a sleeve open. That is stated, not hidden.

Hover: the label takes a 1px ink underline, 3 below its baseline, and nothing else changes. The system has no fills to change, and a thicker box would read as the heavy rule §3 rules out. Keyboard focus: a 2px ink outline, offset 2 outside the box, on keyboard focus only. It is distinct from hover, so a reader who uses both can tell which control the keyboard is on. The same ring marks the cover as a trigger on the record page, from §M.1. Both are provisional until the build step captures them.

Withdrawn within §M.6: the same ring, outside the box, marking the cover as a trigger. Code built it as ruled, and it does not show: the cover is flush to its cell and the cell clips its overflow, so a ring outside the box is outside the cell. Read as pixels, focused against unfocused, nothing changed on any side at 390 or 1440. Moved 4 inside the square as a positive control, 3,792 pixels changed, which is a 2px ring’s own count. So it was faithfully built and wrong, and the entry is owed. With it, the trigger had no sign for a keyboard reader, and §M.1’s pointer signs were the cursor alone.

On the cover, the focus ring is drawn inside the square: 2px of paper at its edge, and 2px of ink inside that. A ring of ink alone inside the square would vanish on a dark photograph as the outside ring vanished on the clip, and paper alone on a light one, so the ring is both, and one of its two bands shows on any photograph. It shows on keyboard focus only, and covers 4px of the cover’s edge while it does. That is the cost, and it lasts only as long as the focus. The case that can defeat it is a cover whose edge is light in places and dark in others, where each band vanishes along part of its run and the ring reads as broken rather than absent. Bitches Brew is probably it, so step 89 captures it. This is scoped to the trigger. The modal’s own controls are boxed with room around them, so their outside ring should show. Code confirms that it does before anything here reaches them. §M.1 points at §M.6’s ring and so now points at this one. Its sentence was false only through the ring this entry withdraws, so it owes no entry of its own.

This rule is scoped to this file and does not settle §G.7. The header’s links are not boxed controls, and their hover starts from a colour that §G.1 changed. They need their own captures. The focus ring is offered to §G.7 as a candidate, and §G.7 settles it, or not, from those captures.

M.7 · The cover’s travel

The modal does not appear: the cover the reader pressed travels from its square on the record page to the modal’s square, growing into place. This is Adam’s ruling. Everything arriving at once read as abrupt, and he expected the record cover to ease to the centre. §M.1 already makes the cover itself the trigger, so the thing pressed becomes the thing that moves.

The travel is one motion, on one curve, an ease-out cubic, so the cover leaves quickly and settles into place. Position, size and the crop all move on it together. The page crops its cover within §33’s bound and the modal fits every face, by §M.4, so the crop eases out to the fit as the cover travels. That is at most 2.5% a side of the photograph’s long side, 2.63% of the square’s, by §M.4, and nothing beyond the bound, where the page fits too. The duration is the same at every width. At 390 × 844 the cover grows to 354 and at 1440 × 900 to 732, so the larger growth moves faster in pixels. One duration keeps it one gesture on every screen, where a duration scaled to distance would make the desktop open slow for no reason a reader has. The duration itself is not ruled: Code proposes it, and Adam judges it from a recording, as he does the turn’s. The curve is chosen here, not inherited. It is the one §W.2 keeps for every motion that is one motion, but that is a ruling about the wall and does not reach the modal by itself.

The travel is flat. It is a move and a growth in the picture plane, with no rotation, so perspective would add only a swell. The perspective §M.5 rules is for the turn and the gatefold’s opening alone, and does not apply to the cover’s travel.

The paper comes up with the cover, rising from clear to opaque over the same duration on the same curve, and the top row, with CLOSE and its hairline, comes with it. Paper first would hide the cover the reader just pressed. Paper after would set a full-size cover over the live page. Rising together, the page gives way as the cover arrives. This is a transition, not a resting state, so it is not the dimming §M.1 rules out: at rest the paper is opaque. So a frame grabbed mid-travel shows the record page through partly opaque paper, by rule. In a still that looks like dimming, and it is not. Step 92’s captures will show it, and they are not a defect.

The face label and the controls arrive after the cover lands, with a short fade that starts at landing, and they do not travel. Arriving with the cover is part of what read as abrupt, and the controls are about the modal, not about the cover’s journey. Code proposes the fade’s length.

Closing plays the travel in reverse, and every way of closing plays it. CLOSE, Escape and Back all close through the same history entry, by §M.1, and all run the same return: the label and controls go first, then the cover travels back to its square on the page while the paper clears. A return that ran on the button alone would leave Back cutting straight to the page. Whatever state the sleeve is in, it shows its front folded before it travels, so what lands in the page’s square is the cover the page shows. The page does not move while the modal covers it, so the square the cover returns to is the one it left. It is still measured at close.

A close is honoured from any state, at any moment, because Back cannot be ignored: once the history entry is gone, the modal is closing whether it is drawn or not, and the same is true mid-turn, mid-way through the gatefold’s opening and mid-travel. So CLOSE, Escape and Back all do the same thing everywhere. The sleeve cuts at once to its folded front, from wherever a turn or the gatefold’s opening has reached, and then travels home. If the close comes while the cover is still travelling in, it reverses from wherever the cover is. The presses ignored mid-motion, here and in §M.5, are the ones that would start another motion. A close ends them all.

The focus ring stays behind. §M.6’s two-band ring is on the page’s trigger, and the cover that travels does not carry it. Focus moves into the modal as §M.1 rules, and on close it returns to the trigger once the cover has landed, so the ring shows again only in the page’s square.

The travelling cover is always a loaded photograph. The modal opens only from the record page, and §33 holds the page’s cover back until its photograph has loaded, so there is no loading case to rule. A photograph that fails is no photograph by §33, and the page shows the no-cover frame in its square. That frame is not a trigger, because the trigger is the displayed cover by §M.1, and there is none. This also settles a record with no photograph at all.

Under the reduced-motion setting, nothing travels. The modal is in place at once, cover, paper, top row, label and controls together, and closing returns at once to the page. §M.5 rules reduced motion the same way for the turn.
