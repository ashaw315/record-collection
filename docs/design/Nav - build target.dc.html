The nav, G — build target

This rules the AppHeader on the twelve screens that carry it, against Code’s inventory of the built header at 390, 1000, 1440 and 1920. Those 48 captures are in the repo, not in this project, so this file has not seen them and shows no specimen. Every ruling here about how something looks is provisional until the header’s build step captures it, and that step’s report edits the section.

G.1 · The header joins the record detail’s system, because the record detail already ruled it

The header is set in the record detail’s system, not kept apart as chrome. This is not a new choice. §4.1 of the settled file counts the header in its label system: “Five nav items, one wordmark”, at 11, mono, uppercase, with .12em tracking “in the nav strip only”. §3 rules the current item’s mark. The built header at 14px sans is a departure from both, of the same kind §12 records for the ← Collection link, and the record detail closed without either being built.

So the header takes §4.1 as written: wordmark and links in Geist Mono 11, uppercase, tracked .12em. Links not current are in the label colour oklch(0.44 0.008 70), not the general muted token. The wordmark is ink. 14 goes, because it is on the ladder nowhere, and 15 is not used, because §4.1 says nothing on the record detail is set at 15. The rule colour, ink, paper and Inter Tight are already shared, and Inter Tight leaves the header, which now has no sans in it.

The weights are the settled file’s drawing, not its prose: 500 for the wordmark and the current link, 400 for the others. The drawing is hand-made and no prose states weights, so weight is the provisional part of this section, settled from the build step’s captures.

No withdrawal is owed for this section. It builds two settled rulings and changes neither.

G.2 · The 53 holds

The header is 53 on one row, unchanged. The record detail’s bands are calculated from it and a test pins it, so this file changes no record-detail ruling and files no withdrawal. Today the 53 comes from the 14px line plus the padding, so smaller type would shrink it. The 53 becomes a property of the box, not of its type: the one-row height is fixed at 53, the type is centred in it, and the vertical padding is whatever is left.

The header’s own row is 53 at every width. Above the width where §G.8’s menu takes over, it holds the wordmark and the five links. Below it, it holds the wordmark and the menu control. The nav never takes a second row. The record detail’s slot is the only thing that can, at narrow widths, and §G.8 rules it.

No other height needs ruling. Code reports that nothing on the record detail reads the header’s height at 390, and nothing in the app reads it at any width. The wall follows the measured height through a CSS variable, and the three tests on the 53 are all above the fork. So the slot’s row and the open menu change the page’s height and nothing that depends on it.

The header’s type is set at line height 1. §4.1 gives size, case and tracking but not line height, and today’s rows carry the old ratio onto 11px type by accident. Every row the header’s type sits in is now a box of fixed height with the type centred: the 53 row, the 44 control and the 44 menu rows. So line height sets nothing but the text’s own box, and at 1 that box is the type, so what is centred is the type and not its leading.

G.3 · The header’s measure is the screen’s

The header’s left edge aligns with the content edge of the screen beneath it, and its measure is that screen’s measure. So it has no cap of its own. Under a screen capped at 1152 it is capped at 1152, and on the record detail it runs the page’s full width, as both do now. The difference between screens was right and this states why.

The inset is ruled here, not inherited. §2.1 gives the record detail “no page margin”, so inheriting that screen’s inset would put the wordmark flush with the window, and that is not intended. The header’s horizontal inset is 18 at every width, on every screen, so on the record detail the wordmark sits over the identity cell’s first line of type. 18 is the identity cell’s padding as §47 rules it, “18px a side, as built”, which is prose and measured. Under a capped screen the 18 is measured from the cap’s edge. This file does not claim that 18 aligns with the content of the capped screens, which have not had their pass.

An earlier draft of this paragraph ruled 34, and it was wrong twice. It took 34 from the settled drawing, which draws the header and the identity cell at 34, but §47 withdrew the cell’s 34 (28/padding-34), so the drawing is stale there and the wordmark would have sat 16 right of the type it was meant to align with. The settled file’s own wrapper is also styled at 34, so the drawing’s figure cannot be told apart from document styling. No figure here comes from a drawing or a document’s styling where prose or a measurement exists. When it was replaced, nothing had been built against the 34 and Code had taken no drop carrying it. Its first drop, 8adf382, came later and carried the 18. So this was a draft fix and no entry is owed.

Links stay 24 apart, as built, on this file’s own reasoning and not on a citation. No settled prose states a gap between nav items. The settled drawing spaces them 46 apart, but that is a value from a drawing, and a wider gap would widen the width at which §G.8’s menu takes over. 24 is provisional on the build step’s captures. The 12 vertical padding and the links’ 8 by 4 go: §G.2 derives the vertical, and the links take no padding of their own.

G.5 · Where the header is, and where it is not

The header is on every screen a signed-in reader can reach, and absent only on Login. Login stays as built and tested. A 404 carries it: a reader who follows a dead record link gets Next’s default page, which has no way back. So the app gets a not-found page of its own, with the header and one line saying what was not found. That is a new screen with its own build step.

The nav never wraps: at the width where it would take a second row, it becomes a menu. This is Adam’s ruling. It overrules the reason the code records, that a menu decides which screens matter and hides the rest behind a tap, and this file does not re-argue it. §G.8 rules the menu.

An earlier draft of this paragraph said that nothing hides and there is no menu, and no entry is owed for replacing it. By WITHDRAWALS.md’s test, a claim is in force when something was built against it or Code has taken a drop carrying it. The built app has no menu, but it was not built against this file: its behaviour predates the target. When the sentence was replaced, Code had taken no drop of this target. Its first was the export at 8adf382, which came after and carried the menu, not this sentence. So the sentence was never in force as this file’s claim, and replacing it was a draft fix. That premise ended at 8adf382: from then on, a change to anything in this file that Code has taken is judged against that drop, as §G.8’s breakpoint was. The built behaviour it described is superseded all the same, so the menu has its own build step and the tests that pin the wrapping are part of what that step changes.

G.6 · The header is not sticky

The header scrolls away with the page on every screen. This was built but never ruled, and the record detail closed on 119 captures of it scrolling. Making it sticky would change a closed screen’s behaviour for no reason a reader has raised. The wall stays in view on Collection at 1440 and 1920 only because that page does not scroll, and this ruling does not depend on that. The build step adds a test that pins it.

G.8 · The menu

The header sets on one row at every width, or it becomes a menu. The width where that happens is measured, not ruled. It is the narrowest width at which the wordmark, the five links with one drawn current, and the record detail’s slot set on one row at §G.3’s 18 inset and 24 gap. The build step measures it and reports it, and Code’s figure is written here from that report. Code’s earlier scan was taken before those values were settled, so it is not the breakpoint. The breakpoint is one width on every screen, taken from the record detail because its row is the widest. The header is one component, and a reader moving from Collection to a record at the same width should not see the nav change form.

Withdrawn within §G.8: the breakpoint taken from the record detail’s row, with Edit and Delete record counted in it. The breakpoint is taken from the nav’s own row instead, by Adam’s decision from the captures. Adam chose from Code’s captures at 390, 600 and 740, in docs/captures/nav-menu/, the way he closed the record detail from its captures. The captures showed what the paragraph above costs. On a record the links went because Edit and Delete record took their room, not because the nav ran out of it, so the app’s navigation was disappearing to make space for one record’s two verbs. The breakpoint is still one width on every screen, and still measured, not ruled. It is the narrowest width at which the wordmark and the five links, with one drawn current, set on one row at §G.3’s 18 inset and 24 gap. The slot plays no part in it.

So the header has four forms, and every boundary between them is a measurement for the build step to confirm. Code’s figures are 584 and 768 on the links’ side and 454 on the menu’s.

  • Where the links and the slot both fit, the links are on one row with the slot in line at the far right, at 53. Code measures this from 768.
  • Where the links fit and the slot does not, the links stay on one row and the slot takes its own row beneath, at 97. Code measures this from 584 to 767.
  • Below the breakpoint, where the control and the slot fit, the MENU control has the slot in line beside it, at 53. Code measures this from 454 to 583.
  • Below that, the MENU control is on the row and the slot takes its own row, at 97.

Only the record detail has the slot, so every other screen has two forms, divided at the breakpoint.

The control is §9.3’s: 44 tall, a 1px ink box, no fill, no radius, border-box, with an 11px mono uppercase ink label tracked .12em like the rest of the header. The label reads MENU, and CLOSE while the menu is open, so the state shows in words and not in a fill this system does not have. It is as wide as its longer label plus 18 a side, not a 44 square. 18 is the header’s inset unit. The longer label is CLOSE, so the box keeps one width in both states and does not jump when it opens, and MENU is centred in it. Code measured MENU at 31.69, so padded for MENU alone the box would be 67.69. Measured: CLOSE is 39.61 in the ruled type, so the control is 75.61 wide. Wordmark and control need 271, and wordmark, control and slot need 454, and both clear the 320 stop. The padding is provisional on capture. No trim of the trailing tracking is ruled, here or anywhere: the build leaves it in, as it does in the record detail’s labels. It sits at the right end of the header’s row with its right edge on the 18 inset, centred vertically in the 53. If centring lands on a half pixel, the extra pixel goes below.

The wordmark survives whole at every width, beside the control. It is the app’s name, and no shortened form exists to fall back to. The build step reports the narrowest width at which the wordmark and the control set on one row 24 apart, and stops if that is wider than 320.

The open menu pushes the page down. It does not cover it. The list sits in the header’s measure directly below its row, on paper, with no shadow or overlay ground. That is how a form that grows below the record detail’s fold behaves, so the menu needs no ground or elevation the system lacks. The menu holds all five links in nav order, and none stays outside it. Each is a row 44 tall, the hit-target floor §9.3 uses, with the label at the 18 inset under the wordmark and a 1px hairline at oklch(0.72 0.004 80) between rows and below the last. Current is marked as §3 rules it, unchanged: ink, 500, and the 2px ink underline 7px below the baseline. A 44 row has room for it, so a stacked list needs no second mark. While the menu is closed, the current section is not shown. That is the cost of the menu, and it is Adam’s ruling that accepts it.

How it opens and closes. The control is a button, aria-expanded set to its state and aria-controls pointing at the list. It follows the wordmark in tab order, and the five links follow it when open. Enter, Space or a click opens and closes it. Escape closes it and returns focus to the control. Choosing a link navigates, and the new page renders with the menu closed. It does not close on scroll or on a click elsewhere, because it covers nothing, so leaving it open costs the reader nothing. How the control and the open rows look on hover and keyboard focus is not ruled, for §G.7’s reason, and the open state adds a third state to the ones waiting on Code’s second pass.

The record detail’s slot stays out of the menu. §24 draws a hairline between the app’s part of the header and the record’s, and the menu is the app’s. Putting Edit and Delete record in it would put this record’s verbs behind the app’s navigation. Where the wordmark, the control and the slot set on one row, the slot sits in line at the far right, after the control and its hairline, as §24 rules. Where they do not, the slot keeps its own row below the header’s row, right-aligned, which is the built state at 390 now. The build step measures and reports that second width. The same rule holds above the breakpoint: the slot sits in line after the links where it fits and takes its own row where it does not, so the nav’s links never give way to it. With the menu open, the slot’s row sits below the list, as the capture at 390 shows.

This changes nothing §24 settled at the widths it was drawn at. The contents, their order, the hairline and the type are unchanged, and so is the place at the far right. But §24 says the verbs sit “in line with the nav” and “cost no height”, and the built record detail at 390 already sets them on a row of their own. The screen closed on captures showing that.
