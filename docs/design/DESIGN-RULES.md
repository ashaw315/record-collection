# Design rules: Claude's standing rules for these documents

- Handoff and WITHDRAWALS.md changes go to Code as change files under `handoff-changes/`, marked prose-only. Never a whole copy of either. Both have two authors. In the handoff, Code writes the step bodies and Done marks. In WITHDRAWALS.md, Claude writes the entries and Code corrects the Build clauses and derives the machine-readable comment. A whole-file replace reverts whatever the other author has added since Claude's copy, and Claude's copy is always behind Code's last correction.
- A change file that edits a target's section says what it does to that section's governs row: either the new description, or "row unchanged" with the reason. A withdrawal that moves a ruling to another section names both rows.
- The handoff export is read-only for Claude. Claude rules against the exported handoff, which carries Code's region, and never against an older copy. Changes go back as change files anchored on repo text, never as a whole copy of the export. A ruling made before the current export arrived names the copy it was made against.
- A ruling lives in its target, and the target travels with any note that names it. A change file can describe a target or carry handoff and WITHDRAWALS.md edits, but it is never the ruling. Code builds to targets, not notes, so a note sent without its target is one Code is right to hold. Each send lists the files it is meant to carry, so a relay that drops one is visible on arrival.
- Anchor every change file on text already in the repo, never on text an earlier change file introduces. Still name the files assumed applied.
- Settle mechanical questions with Code directly and report after: whether a withdrawal is owed, whether something is a draft fix, and where a withdrawal sentence goes. Bring to the user only disagreements with Code, or cases the written rules do not reach.
- The channel to Code: requests to Code go in the change files. Code's requests to Claude arrive in a block headed FOR DESIGN in Code's reports. Neither waits on the user.
- Specimens and sheets come from the build at a stated viewport, never drawn by hand. If one cannot be generated, say so.
- Rulings about appearance are provisional until built. Each provisional gets a line in the handoff's Provisionals list, closed by the step report that returns it.
- Claude never writes a file another author owns, including CLAUDE.md.
- Every withdrawal entry's description ends with a Build clause, saying whether the build followed the withdrawn claim: followed, did not follow, believed to follow (with the source), or nothing to follow. When the entry is filed, I state only what Code has reported. The intake confirms or corrects a clause that a drop can settle. A "believed to follow" is closed only by the step that runs the build and confirms it, and that step's report names the entry. Where the build held something that matches neither the withdrawn claim nor the live one, the clause says so in its own words rather than forcing a category. A withdrawal the build still follows is open work, not a closed record.
- Describe what was observed, and leave the mechanism unstated until something has measured it. A cause reasoned from a symptom goes in as "believed", with its source, or not at all. That applies most of all in an entry, because the entry is the record.
- When a step's condition is restated, re-derive any instrument the step names: ask which state each instrument makes, and match it to the condition. Re-deriving is not replacing. An instrument that makes a different state stays, named for the state it makes, whether that is the held case, the not-held case, or a control for a state production never reaches. A step names each instrument it keeps beside the state it makes, so the next restatement can re-derive from the list instead of from memory.
