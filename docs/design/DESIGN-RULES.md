# Design rules: Claude's standing rules for these documents

- Handoff and WITHDRAWALS.md changes go to Code as change files under `handoff-changes/`, marked prose-only. Never a whole copy of either. Both have two authors. In the handoff, Code writes the step bodies and Done marks. In WITHDRAWALS.md, Claude writes the entries and Code corrects the Build clauses and derives the machine-readable comment. A whole-file replace reverts whatever the other author has added since Claude's copy, and Claude's copy is always behind Code's last correction.
- A change file that edits a target's section says what it does to that section's governs row: either the new description, or "row unchanged" with the reason. A withdrawal that moves a ruling to another section names both rows.
- The handoff export is read-only for Claude. Claude rules against the exported handoff, which carries Code's region, and never against an older copy. Changes go back as change files anchored on repo text, never as a whole copy of the export. A ruling made before the current export arrived names the copy it was made against.
- A ruling lives in its target, and the target travels with any note that names it. A change file can describe a target or carry handoff and WITHDRAWALS.md edits, but it is never the ruling. Code builds to targets, not notes, so a note sent without its target is one Code is right to hold. Each send lists the files it is meant to carry, so a relay that drops one is visible on arrival.
- Anchor every change file on text already in the repo, never on text an earlier change file introduces. Still name the files assumed applied.
- Settle mechanical questions with Code directly and report after: whether a withdrawal is owed, whether something is a draft fix, and where a withdrawal sentence goes. Bring to the user only disagreements with Code, or cases the written rules do not reach.
- The channel to Code: requests to Code go in the change files. Code's requests to Claude arrive in a block headed FOR DESIGN in Code's reports. Neither waits on the user.
- Specimens and sheets come from the build at a stated viewport, never drawn by hand. If one cannot be generated, say so.
- Rulings about appearance are provisional until built. Each provisional gets a line in the handoff's Provisionals list, closed by the step report that returns it.
- Claude never writes a file another author owns, including CLAUDE.md.
- Every withdrawal entry's description ends with a Build clause, saying whether the build followed the withdrawn claim: followed, did not follow, believed to follow (with the source), or nothing to follow. When the entry is filed, I state only what Code has reported. The intake confirms or corrects a clause that a drop can settle. A "believed to follow" is closed only by the step that runs the build and confirms it, and that step's report names the entry. Where the build held something that matches neither the withdrawn claim nor the live one, the clause says so in its own words rather than forcing a category. A withdrawal the build still follows is open work, not a closed record.
- Describe what was observed, and leave the mechanism unstated until something has measured it. A cause reasoned from a symptom goes in as "believed", with its source, or not at all. That applies most of all in an entry, because the entry is the record.
- When a step's condition is restated, re-derive any instrument the step names: ask which state each instrument makes, and match it to the condition. Re-deriving is not replacing. An instrument that makes a different state stays, named for the state it makes, whether that is the held case, the not-held case, or a control for a state production never reaches. A step names each instrument it keeps beside the state it makes, so the next restatement can re-derive from the list instead of from memory.
- A withdrawal that reinstates a claim an earlier entry withdrew says "Reinstates `id`" in its description and names the round trip, so a reader sees the loop without reconstructing it. No assertion detects a reinstatement, so the pointer is the only trace. Two round trips in two days, the pan and §W.23, are the reason.
- A change file places each new WITHDRAWALS.md entry under its target's heading, after that heading's last entry. The main list holds only the record-detail targets' entries, and assertion 11 refuses an entry from any other target there.
- A target sentence that says what a test does is written in the stated form: "the test asserts", "the test sets" or "the test clicks". A test written for it carries a marker naming the section and quoting the phrase, and assertion 13 pairs the two. A test sentence outside the form is a choice to leave it unchecked, made where it can be seen. Say why in the same paragraph, or reword it into the form. A paired sentence shows that a test exists, not that it checks what the sentence says, so reading the test stays a person's job. The reason: §W.8 named a test for weeks that nobody had written, and once written it found two defects.
- When a drop is refused, ask what the refusal said before changing anything. The refusal names its assertion, and for assertion 6 the entry or the stale comment. A cause inferred from the file is a guess, and a correction made on a guess can fix something that was not broken while the real cause sits elsewhere. The reason: on 4 Nov a refusal by assertion 6, a stale derived comment, was answered by resending an anchor that had matched the first time.
- A figure that names a record is a record of one measurement, and is written with the collection's size and the build it came from. A test asserts the rule the figure illustrates, never the figure. The reason: on 6 Nov, §55's figures from a 17-record collection no longer matched 55 records, and nobody could say whether they had come from a production build.
- Each send states the state of each of Claude's change files against the latest export, by file name: offered for download, relayed by Adam, or landed. A file not yet landed carries the date it was offered and the date it was relayed, and these are kept separate where they differ, so a loss shows whether it happened before the relay or after it. A file offered or relayed and absent from two consecutive exports taken after it was offered is flagged in the list itself. Code's export bundle lists, by name, every change file it has applied. A file in Claude's list and missing from Code's never arrived. A file in Code's list and not in Claude's is one Code applied that Claude doesn't own, and is reported. The reason: "First paint is styled" was offered on 5 Nov and absent from two exports, so §43's ruling sat in the repo for a day with no step. A list that only compares landed against not-landed reports that truthfully every time and fires never. It was found because someone asked.
- A change file that supersedes, replaces or absorbs another says so in its own header, by name, and Code records both names at intake. Code sees only the name on the file it receives, so a file folded into another under a new name can't be told from one that was lost. The reason: on 7 Nov, five of Claude's files were absent from Code's applied list though their content had landed.
- A change file that edits a step anchors on Claude's own unnumbered copy, the line headed "Unnumbered, for Code to number", never on Code's numbered Done line above it.
- A change file names every ruling the cards it travels with carry since each card's last send, including rulings its own changes don't touch, and says which change file carries each one's step. A card is the whole document, so whatever it holds lands when it lands, and a ruling the change file doesn't name lands with no step and no record of which change brought it. The reason: on 6 Nov, §43's first-paint ruling arrived inside the card for "Rules not snapshots", whose change file said it touched neither that nor the tracklist. The unnumbered line is Claude's and carries the quote, and the Done line is Code's record of what was built. A change to the instruction after a Done leaves the Done describing the old wording until Code builds the change, so the change file says the step is built against an earlier wording.
- A rule whose evidence can't appear in a capture is checked by an assertion in the suite, never by a capture. Newest first, upload order, a time and a stored value are its kind. A capture checks only what it can show. And a rule that carries a figure is passed by Code's measurement from the build, not by a reading of the capture by eye. The reason: on 8 Nov, §62's newest first could not be read from colours, and four of Q2's and Q3's passes were read by eye.
